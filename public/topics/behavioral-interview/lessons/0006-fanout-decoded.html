⬡ Lesson 06 · Deep dive

Fan-out, decoded:
who reads what, and how.

One grill probe caused confusion: "How did downstream services read this? One big table?" The answer is two separate paths out of your service — one you designed for the whole company (the event fan-out), one you kept for yourself (the persisted table). Confusing them is what makes the model answer feel dense. This lesson separates them, visually, for good.

↑ Part of the course · prev: The Architecture Grill (probe deck) · story source: my-stories.md (Story 1)

1First, the trap: "one big table"

The interviewer hands you the lazy answer. Taking it means every service in the company reads your database. Watch what that looks like — five teams, one Postgres:

Shared dependency

Your DB is now load-bearing for the whole company. A slow query or sale-day write spike on your side becomes everyone's latency.

Schema = public API

You can't rename a column without breaking five teams. The "microservice" boundary evaporates — that's a distributed monolith.

Polling latency

Readers must ask "anything new for order 123?" over and over. Latency = poll interval; cost = wasted queries when nothing changed.

A senior candidate flinches at "one big table." The question is bait — the flinch is the answer's opening move.

2What we built: two paths out

The normalized event leaves the service twice, for two different audiences. Purple = the ingest you know. Teal = Path A, push (real-time fan-out). Amber dashed = Path B, pull (queries & audit).

Path A · the event · push · real-time

"Tell me the moment a package moves."

The service publishes the normalized event; each downstream service gets its own copy, delivered to its own queue, pushed the moment it happens. Nobody polls, nobody touches your database, nobody sees a partner format. This path is the "one source of truth" from your pitch.

Path B · the table · pull · queries

"Show me everything that ever happened to order 123."

The service also persists events to Postgres. That table serves lookups and audit — support tools, debugging, history. It's yours, behind your service boundary. It is not the company's integration point; it's the memory your service keeps.

Why this shape wins: push beats poll for latency; per-consumer queues mean one slow consumer backs up only itself (its own DLQ, its own redelivery — the SQS lessons apply to them too); and your table stays a private implementation detail you can reshape anytime.

3The follow-up: "fan-out how, exactly?"

One queue can't fan out — with a single SQS queue, consumers are competing (each message goes to exactly one consumer, which is right for your ingest, wrong for broadcasting). The standard AWS pattern for "every consumer gets every message" is SNS → one SQS queue per consumer — the "fan-out" pattern:

Each consumer owns its queue: its own visibility timeouts, its own DLQ, its own retry policy. One consumer falling behind is invisible to the others. If Cencosud's actual mechanism differed (e.g. EventBridge), say that name instead — the shape (broadcast → per-consumer buffer) is what matters.

4The model answer, sentence by sentence

"Two paths." The frame. It tells the interviewer you're about to separate real-time consumption from query/audit — before they ask. Framing first is the senior move.
"fanned the normalized event out… each service got its own copy pushed to its own queue" Path A, concretely: broadcast + per-consumer queue. "Its own copy" and "its own queue" are the two facts that prove it's a real fan-out, not a shared table.
"nobody polled and nobody touched our database" The anti-trap, stated as a property: no polling latency, no shared dependency. You flinched at "one big table" and named what you did instead.
"the Postgres table… served the query side — support lookups, audit, package history" Path B, bounded. The table exists, has a job, and the job is narrow. Listeners of the job description: lookups, audit, history — all query-shaped.
"the design object… was the internal event schema: one versioned contract" The schema is the public API; the table is an implementation detail. Swap: "the table was ours to change; the schema was public, so it evolved additively only." That's contract ownership — the org-level skill.
"partner quirks stopped at the normalizer" The payoff sentence. From downstream's point of view there is one format, forever. Partner churn is invisible outside the service.

530-second interview version

"Two paths. Real-time consumers subscribed to the internal tracking event — the service fanned each normalized event out to every consumer's own queue, so nobody polled and nobody touched our database; one slow consumer backed up only itself. The Postgres table we persisted served the query side: support lookups, audit, package history. And the design object I actually cared about was the event schema — one versioned contract. The table behind it was ours to change; the schema was public, so it evolved additively only."
