1O que é igual (e por que é igual por natureza)What's alike (and why it's alike by nature)

Mesma matemáticaSame math

Ambos são bancos relacionais: tabelas, linhas, PK/FK, JOIN, Normalização. O modelo — chaves e relações — veio antes de qualquer marca. Trocar de um pro outro não muda seu desenho de dados.Both are relational databases: tables, rows, PK/FK, JOIN, normalization. The model — keys and relations — predates either brand. Switching between them doesn't change your data design.

Mesmas promessasSame promises

Ambos entregam ACID com transações (BEGIN … COMMIT), isolamento via MVCC (leitores não bloqueiam escritores) e índices B-tree por padrão. O "P" de Primary Key e o "J" de JOIN funcionam igual.Both deliver ACID with transactions (BEGIN … COMMIT), isolation via MVCC (readers don't block writers), and B-tree indexes by default. The "P" in Primary Key and the "J" in JOIN work the same.

Mesmo dialeto no dia a diaSame dialect day to day

95% do seu SQL é portátil: SELECT, WHERE, JOIN, GROUP BY, agregações, LIMIT, INSERT. Os 5% que quebram ao migrar são: tipos, coerção, e cláusulas especiais — a seção 3.95% of your SQL is portable: SELECT, WHERE, JOIN, GROUP BY, aggregates, LIMIT, INSERT. The 5% that break on migration: types, coercion, and special clauses — section 3.

3A sintaxe que quebra na migraçãoThe syntax that breaks on migration 

# concatenação
Postgres:  SELECT first_name || ' ' || last_name;
MySQL:     SELECT CONCAT(first_name, ' ', last_name);

# upsert + pegar o id de volta
Postgres:  INSERT INTO users (email) VALUES ($1)
           ON CONFLICT (email) DO UPDATE SET seen = now()
           RETURNING id;
MySQL:     INSERT INTO users (email) VALUES (?)
           ON DUPLICATE KEY UPDATE seen = NOW();
           -- depois: SELECT LAST_INSERT_ID();

# JSON: campo aninhado
Postgres:  SELECT data->>'city' FROM events;
MySQL:     SELECT JSON_EXTRACT(data, '$.city') FROM events;# concatenation
Postgres:  SELECT first_name || ' ' || last_name;
MySQL:     SELECT CONCAT(first_name, ' ', last_name);

# upsert + getting the id back
Postgres:  INSERT INTO users (email) VALUES ($1)
           ON CONFLICT (email) DO UPDATE SET seen = now()
           RETURNING id;
MySQL:     INSERT INTO users (email) VALUES (?)
           ON DUPLICATE KEY UPDATE seen = NOW();
           -- then: SELECT LAST_INSERT_ID();

# JSON: nested field
Postgres:  SELECT data->>'city' FROM events;
MySQL:     SELECT JSON_EXTRACT(data, '$.city') FROM events;

4O que derruba todo mundoWhat trips everyone up

Case sensitivity não é do SQL — é do sistema. Postgres dobra todo identificador sem aspas para minúsculas. MySQL depende do sistema de arquivos: Users e users podem ser a mesma tabela no Linux e tabelas diferentes no macOS. Migração cruzada de SO é onde isso morde.Case sensitivity isn't SQL's — it's the OS's. Postgres folds every unquoted identifier to lowercase. MySQL follows the filesystem: Users and users can be the same table on Linux and different tables on macOS. Cross-OS migrations are where this bites.

Segundo susto: strings e números. No MySQL, WHERE id = '42' funciona e o índice ainda é usado. No Postgres, a mesma query pode dar erro de tipo — ele se recusa a adivinhar. Terceiro: no MySQL histórico, utf8 não era UTF-8 de verdade (3 bytes, sem emoji) — o nome correto é utf8mb4. Postgres sempre foi UTF-8 completo.Second scare: strings and numbers. In MySQL, WHERE id = '42' works and the index is still used. In Postgres the same query can raise a type error — it refuses to guess. Third: in legacy MySQL, utf8 wasn't real UTF-8 (3 bytes, no emoji) — the correct name is utf8mb4. Postgres was always full UTF-8.

Escolha pela carga, não pela fama. Cargas analíticas, JSON pesado, geografia e extensões → Postgres. Muita leitura simples, ecossistema LAMP/W ordem-establishment, operação batida → MySQL. Ambos escalam além do que 99% dos produtos precisam.Choose by workload, not fame. Analytical loads, heavy JSON, geo, and extensions → Postgres. Lots of simple reads, established LAMP-ecosystem tooling, boring operations → MySQL. Both scale past what 99% of products need.

5A jogada de entrevista (30 segundos)The interview move (30 seconds) 

# o mesmo design nos dois bancos: chaves e JOIN não mudam
SELECT o.id, COUNT(i.id) AS items
FROM orders o
JOIN order_items i ON i.order_id = o.id
WHERE o.status = 'paid'
GROUP BY o.id;

# o que muda é a borda: upsert, json, retorno de id
Postgres:  ON CONFLICT … RETURNING id      -- estrito, uma viagem
MySQL:     ON DUPLICATE KEY UPDATE         + LAST_INSERT_ID()# the same design on both: keys and JOINs don't change

Frase que fecha a questão: "Os dois são relacionais ACID com MVCC e B-tree — o desenho de dados é idêntico. Postgres é estrito e rico: JSONB com GIN, ON CONFLICT com RETURNING, arrays e extensões, mas paga VACUUM. MySQL é pragmático: coerção implícita, ON DUPLICATE KEY, operação simples. Eu escolho pela carga: JSON e análise → Postgres; leitura simples e stack batida → MySQL."The sentence that closes the question: "Both are ACID relational databases with MVCC and B-trees — the data design is identical. Postgres is strict and rich: JSONB with GIN, ON CONFLICT with RETURNING, arrays and extensions, but pays for VACUUM. MySQL is pragmatic: implicit coercion, ON DUPLICATE KEY, simple operations. I pick by workload: JSON and analytics → Postgres; simple reads and a familiar stack → MySQL."
