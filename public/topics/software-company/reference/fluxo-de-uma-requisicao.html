2Por que "mesma origem" é tudoWhy "same origin" is everything

O browser só anexa o cookie automaticamente quando o destino é a mesma origem (mesmo domínio+porta). É por isso que no dev existe o proxy do Vite: ele faz /api parecer vir do próprio frontend (localhost:4321), então o cookie vai. Em produção, um reverse proxy (nginx/Caddy) faz o mesmo — ou tudo quebra.The browser only attaches the cookie automatically when the destination is the same origin (same domain+port). That's why dev has the Vite proxy: it makes /api look like it comes from the frontend itself (localhost:4321), so the cookie travels. In production a reverse proxy (nginx/Caddy) does the same — or everything breaks.

Se um dia separar frontend e API em domínios diferentes: o cookie para de viajar. Teria que trocar SameSite=Lax por None + Secure (HTTPS). Por isso o design prefere mesma origem.If you ever split frontend and API into different domains: the cookie stops traveling. You'd have to switch SameSite=Lax to None + Secure (HTTPS). That's why the design prefers same origin.

3O truque do SSR: repassar o cookieThe SSR trick: forwarding the cookie

No servidor (Node), o fetch é "burro": ele não conhece o browser, não envia o cookie do usuário. Então o api.ts pega o cookie do pedido original e cola manualmente no header ao chamar o .NET.On the server (Node), fetch is "dumb": it doesn't know the browser, it doesn't send the user's cookie. So api.ts takes the cookie from the original request and pastes it manually into the header when calling .NET. 

// SSR: Node precisa de URL absoluta + repassa o cookie do browser
headers: { ...(cookie ? { Cookie: cookie } : {}) }

Exercício ativo: apague essa linha do api.ts. Auth quebra nas páginas SSR, mas funciona no cliente (React ilha). Sentiu a diferença?Active exercise: delete that line in api.ts. Auth breaks on SSR pages but still works on the client (React island). Feel the difference?

6O caminho de volta + o 401The way back + the 401

A resposta sobe o mesmo caminho. Atenção ao 401: o .NET, por padrão, redireciona (302) pra login em não-autenticado — mas isso é pra app MVC. Pra uma API consumida por fetch, redirecionar é errado. Por isso o Program.cs sobrescreve:The response climbs back the same way. Watch the 401: by default .NET redirects (302) to login when unauthenticated — but that's for an MVC app. For an API consumed by fetch, redirecting is wrong. So Program.cs overrides it: 

// API devolve o status puro — não redireciona// API returns the raw status — it does not redirect
options.Events.OnRedirectToLogin = ctx => { ctx.Response.StatusCode = 401; return Task.CompletedTask; };

Aí cada camada decide o que fazer com o 401: no cliente (React ilha), o api.ts manda pra /login. No SSR, vira "anônimo" (não quebra a página). Duas camadas, um mesmo evento.Then each layer decides what to do with the 401: on the client (React island), api.ts sends to /login. In SSR, it becomes "anonymous" (doesn't break the page). Two layers, one same event.
