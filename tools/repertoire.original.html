P3 Trabalho lento: fila + workerSlow work: queue + worker L2

Email, relatório, thumbnail — "grava rápido, processa depois".Email, report, thumbnail — "record fast, process later".

  3. Seta API → DB ("transação: job queued + outbox")Arrow API → DB ("transaction: queued job + outbox")

Fale enquanto desenha: "A API grava job + outbox na mesma transação e responde na hora com 202 + jobId. O publisher envia o outbox à SQS. O worker faz poll, executa o trabalho lento, marca accepted — e só então chama DeleteMessage." E feche com: "SQS pode reentregar, então o worker é idempotente. Sem delete, a mensagem volta após o timeout de visibilidade e, no limite, vai pra DLQ."Say while drawing: "The API writes the job + outbox in one transaction and responds immediately with 202 + jobId. The publisher sends the outbox to SQS. The worker polls, does the slow work, marks accepted — and only then calls DeleteMessage." And close with: "SQS may redeliver, so the worker is idempotent. Undeleted messages return after the visibility timeout and eventually move to a DLQ."

Por quê SQS (e não Kafka, ainda): o trabalho falha por mensagem — em SQS, mensagem sem delete volta após o timeout de visibilidade, e a redrive policy pode movê-la à DLQ. Kafka seria canhão de mais para um único consumidor sem replay. Tradeoff pronto: SQS Standard entrega pelo menos uma vez — worker precisa ser idempotente. Gravar no DB e publicar direto na fila seriam duas escritas — o job poderia ser gravado e a publicação falhar. O diagrama usa outbox transacional: a API grava job + evento na mesma transação; um publisher lê o outbox e publica na SQS. E se o cliente perde o 202 e reenvia? A API aceita idempotency-key pra não duplicar o job.Why SQS (not Kafka, yet): work fails per message — in SQS, an undeleted message reappears after its visibility timeout, and a redrive policy can move it to a DLQ. Kafka is overkill for a single consumer with no replay. Ready tradeoff: SQS Standard delivers at least once — the worker must be idempotent. Writing to the DB and publishing directly to the queue would be two writes — the job could commit while the publish fails. The diagram uses a transactional outbox: the API writes job + event in one transaction; a publisher reads the outbox and publishes to SQS. And if the client loses the 202 and retries? The API accepts an idempotency key so the job isn't duplicated.

O fluxo na íntegra: 1–3 a API confirma job + outbox atomicamente, responde na hora, e o publisher entrega o outbox à SQS — o cliente nunca espera o trabalho lento. 4–5 o worker puxa a mensagem (a fila não empurra), sob um timeout de visibilidade: ela fica invisível para os outros workers enquanto ele processa. 6–8 envia e grava accepted depois do ok — mas ok do provedor é aceito, não entregue; a cadeia real é queued → processing → accepted → delivered/failed, e o delivered chega depois, por webhook. 9 chama DeleteMessage após o sucesso; mesmo assim, SQS Standard pode raramente reentregar, então o worker continua idempotente. Se o worker não deleta — falhou ou morreu —, o timeout expira, a mensagem volta a ficar visível e é reentregue. Cada recebimento conta; no maxReceiveCount, a política de redrive move a mensagem pra DLQ, onde pode ser inspecionada, alertada e reproduzida; um consumidor da DLQ (ou reconciliação) marca o job como failed. Sem DLQ, uma mensagem venenosa tenta novamente até expirar o período de retenção.The full flow: after the API commits job + outbox, it responds instantly while the publisher sends the outbox to SQS — the client never waits for the slow work. 4–5 the worker pulls the message under a visibility timeout. 6–8 send, then record accepted; the provider's ok means accepted, not delivered, and delivered/failed arrives later through an authenticated webhook endpoint. 9 calls DeleteMessage after success; SQS Standard can still rarely redeliver, so the worker remains idempotent. Without a delete, the timeout expires and the message becomes visible again. Each receive counts; at maxReceiveCount the redrive policy moves it to the DLQ for inspection, alerting, and replay. Without a DLQ, a poison message retries until its retention period expires.

Fale enquanto desenha: "A API cria um registro pending e devolve uma URL assinada pro autor. O payload grande vai direto pro S3; o evento do S3 confirma a chegada. Por quê S3 e CDN: S3 escala sem pré-provisionar armazenamento e é projetado para durabilidade — guardar vídeo em disco de servidor (ou BLOB no Postgres) é caro e frágil. CDN porque o mesmo vídeo é baixado milhões de vezes: servir da origem queima banda e adiciona latência; a borda responde perto do usuário. E o processamento? CDN because the same video is downloaded millions of times: serving from origin burns bandwidth and adds latency; the edge answers close to the user. And processing? S3 emits an event → queue → worker (blueprint P6). In the data plane the CDN never talks to the API — its origin is S3; the API only authorizes (signed URLs) and purges the cache. For dynamic content, the CDN's origin can be the API itself.

P5 Rate limiter: contador atômicoRate limiter: atomic counter L2

"Máximo 100 pedidos por minuto por usuário." Redis é uma opção comum e de baixa latência para esse contador compartilhado atômico."Max 100 requests per minute per user." Redis is a common low-latency store for this atomic shared counter.

Ordem de desenhoDraw order

  1. Cliente → API ×NClient → API ×N
  2. Redis à direita: "INCR + EXPIRE no 1º (Lua)", chave rate-limit:{userId}:{window}Redis on the right: "INCR + EXPIRE on 1st (Lua)", key rate-limit:{userId}:{window}
  3. Setas API ↔ Redis ("INCR + EXPIRE", volta "count") — o Redis conta; quem decide e responde 429 é a APIArrows API ↔ Redis ("INCR + EXPIRE", back "count") — Redis counts; the API decides and answers the 429
  4. Seta vermelha API → cliente: acima do limite → 429 (com Retry-After, RateLimit e RateLimit-Policy)Red arrow API → client: over the limit → 429 (with Retry-After, RateLimit, and RateLimit-Policy)
  5. Abaixo do limite → handler (o resto de P1/P2)Under the limit → handler (the rest of P1/P2)

Fale enquanto desenha: "Cada pedido roda INCR + EXPIRE atômicos no Redis — o EXPIRE só quando o contador nasce — e o Redis devolve o count. A API decide: passou de 100 no minuto? 429, sem tocar o resto do sistema. O Redis é compartilhado — não importa em qual instância o pedido caiu."Say while drawing: "Each request runs an atomic INCR + EXPIRE in Redis — EXPIRE only when the counter is born — and Redis returns the count. The API decides: over 100 in the minute? 429, without touching the rest of the system. Redis is shared — it doesn't matter which instance got the request."

Por quê Redis: "checar e incrementar" precisa ser uma operação atômica — em duas chamadas separadas, duas instâncias leem 99 ao mesmo tempo e deixam passar 101. Contador em linha do Postgres criaria lock por usuário a cada request. O Lua é mínimo: INCR; se count == 1, EXPIRE — a janela nasce no 1º hit e não reseta a cada request — e o Redis devolve o count; a API decide: ≤ 100 segue, > 100 responde 429 com Retry-After e RateLimit / RateLimit-Policy. Tradeoff pronto: janela fixa permite rajada na virada (200 em torno do limite); janela deslizante evita essa borda, e token bucket troca a borda por uma rajada configurável.Why Redis: "check and increment" must be one atomic operation — in two separate calls, two instances both read 99 and let 101 through. A counter row in Postgres would create a per-user lock on every request. The Lua is minimal: INCR; if count == 1, EXPIRE — the window is born on the first hit, not reset per request — and Redis returns the count; the API decides: ≤ 100 continues, > 100 answers 429 with Retry-After and RateLimit / RateLimit-Policy. Ready tradeoff: a fixed window permits a boundary burst (200 around the minute edge); a sliding window avoids that edge, while a token bucket replaces it with configurable burst capacity.
