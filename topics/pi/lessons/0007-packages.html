A Pi package bundles the four primitives — extensions, skills, prompts, themes — and ships them via npm or git. This is how Pi scales from "my personal setup" to a reusable, shareable toolkit. It's also where the security stakes get real.

1A package = the four primitives, bundled

You've met each primitive in lessons 4–6. A package just boxes them together and gives the box a name, a version, and a distribution channel.

The arc, completed: lessons 4–6 taught the primitives. Packages compose them and make them portable — the same primitives, now installable in one command and shareable with anyone.

2Install & manage

Three source types, one command. Default writes to user settings; -l writes to project (shareable, auto-installed after trust).

pi install git:github.com/u/repo@v1 # pinned tag/commit
pi -e npm:@foo/bar                 # try without installing (temp, one run)
pi install -l git:github.com/u/repo # -l → project settings (.pi/)

pi remove npm:@foo/bar
pi update --all                    # pi + packages + reconcile pinned git refs
pi update npm:@foo/bar             # update one

3Pinning & updates

A version (@1.2.3) or ref (@v1) pins a package. Pinned packages are skipped by pi update --extensions / --all — they don't drift. To move a pinned package, re-install at a new ref.

📌 Pinned @ref

Reproducible. Updates skip it, but still reconcile the clone to the configured ref. Move with pi install …@new-ref.

🌀 Floating (no ref)

Latest. pi update --extensions moves it forward. Fine for experimentation, risky for teamwork.

For shared/team setups: pin. A project .pi/settings.json with pinned packages means every teammate gets the same capabilities — Pi auto-installs missing ones on startup after trust.

4Creating your own

Add a pi key to package.json (or just use conventional dirs) and tag it pi-package. That's the whole publishing step. 

// package.json
{
  "name": "my-pi-toolkit",
  "keywords": ["pi-package"],
  "pi": {
    "extensions": ["./extensions"],
    "skills":     ["./skills"],
    "prompts":    ["./prompts"],
    "themes":     ["./themes"],
    "video": "https://…/demo.mp4"   # optional gallery preview
  }
}

No manifest? Auto-discover. Without a pi key, Pi loads from extensions/ (.ts/.js), skills/, prompts/ (.md), themes/ (.json).

Deps rule: runtime deps → dependencies. Core Pi libs (pi-ai, pi-tui, typebox…) → peerDependencies: "*", don't bundle.

5Security — read this twice

Pi packages run with your full system access. Extensions execute arbitrary code; skills can instruct the model to perform any action — including running executables. Review the source before installing anything third-party. Same hygiene as npm install, but the blast radius includes "the model following untrusted instructions."

🔍

Read the code

Extensions = TS you'll execute. Skim the entry point + any child_process/fetch.

🚪

Trust gates it

Project packages load only after the trust prompt. /trust saves the decision.

🧪

Try first

pi -e <source> runs it from a temp dir for one session — inspect before committing.

6Filter & enable/disable

Don't want everything a package ships? Narrow it with the object form, or toggle individual resources with pi config. 

// settings.json — take only what you want
{
  "packages": [
    "npm:simple-pkg",
    {
      "source": "npm:my-package",
      "extensions": ["extensions/*.ts", "!extensions/legacy.ts"],
      "skills": [],                       # load none
      "themes": ["+themes/legacy.json"]    # force-include
    }
  ]
}
pi config

Toggle extensions/skills/prompts/themes on or off. Tab switches global↔project; -l starts in project.

scope & dedup

Same package in global + project? Project wins — unless it sets autoload: false, then it's a delta over global.
