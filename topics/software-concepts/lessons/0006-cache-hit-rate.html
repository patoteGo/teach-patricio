Hits são sempre rápidos. A taxa protege os misses.Hits are always fast. The hit rate protects the misses.

Um hit custa ~2ms — nunca é o problema. A pergunta real é: quantos misses chegam ao banco, e com que carga ele está quando chegam. A taxa de hit é um dial de carga, e a fórmula se deriva — não se decora.A hit costs ~2ms — never the problem. The real question is: how many misses reach the DB, and how loaded it is when they do. The hit rate is a load dial, and the formula is derived — not memorized.

Taxa de hit = requisições servidas do cache ÷ total. 95 de 100 redirects acham o mapeamento no cache → 95%. Os outros 5 são misses que caem para o banco. Siga a cadeia:Hit rate = requests served from cache ÷ total. 95 of 100 redirects find the mapping cached → 95%. The other 5 are misses that fall through to the DB. Follow the chain: 

hit rate  →  quanto tráfego chega ao banco  →  carga do banco  →  quão rápido é um miss

Um cache fraco não ajuda pouco — ele atrapalha. Se a taxa for baixa, o banco fica sobrecarregado e até os misses ficam lentos. 300ms+ perto de 100% de utilização, via teoria de filas.A weak cache doesn't just help less — it hurts. If the rate is low, the DB gets overloaded and even misses crawl. 300ms+ near 100% utilization, by queueing theory.

5MySQL, PostgreSQL ou NoSQL?MySQL, PostgreSQL, or NoSQL?

O modelo é simples demais para decidir por você: short_code (PK) → long_url, created_at, user_id, expiry — uma linha, um lookup por PK. Qualquer engine guarda isso. O trade-off está em escalar leituras, custo operacional, e o que você abre mão.The model is too simple to decide for you: short_code (PK) → long_url, created_at, user_id, expiry — one row, one PK lookup per read. Any engine stores that. The trade-off is in scaling reads, ops burden, and what you give up.

MySQL padrão chatoboring default

  • Replicação madura (primary → réplicas), enorme pool de ops.Mature replication (primary → replicas), huge ops talent pool.
  • Lookups por PK são exatamente o que a InnoDB faz de melhor.PK lookups are exactly what InnoDB does best.
  • Otimizador mais fraco que o Postgres para queries não-triviais.Weaker planner than Postgres for non-trivial queries.
  • Recursos mais estreitos (tipos, full-text, JSON).Narrower features (types, full-text, JSON).

PostgreSQL melhor padrão hojebest default today

  • Planner e tipos melhores — paga quando o produto cresce além do redirect (analytics, expiração, metadados JSON).Better planner and types — pays off when the product grows past redirects (analytics, expiry, JSON metadata).
  • Um banco evita rodar um segundo sistema depois.One DB avoids running a second system later.
  • Replicação historicamente mais manual que a do MySQL.Replication historically more manual than MySQL's.
  • Processo por conexão — precisa de pooler (pgbouncer) em alto volume de conexões.Process per connection — needs a pooler (pgbouncer) at high connection counts.

NoSQL escala que você não temscale you don't have

  • Escala horizontal nativa: adiciona nós, ganha QPS, sem primary único.Native horizontal scaling: add nodes, get QPS, no single primary.
  • Padrão key-value (get/put por short_code) cabe perfeito em DynamoDB/Cassandra.Key-value access (get/put by short_code) fits DynamoDB/Cassandra perfectly.
  • Perde transações, joins e SQL ad-hoc — analytics e migrações doem.Loses transactions, joins, ad-hoc SQL — analytics and migrations hurt.
  • Outro sistema para operar (ou pagar); lock-in com Dynamo. Overkill a 1.200 QPS.Another system to operate (or pay for); Dynamo lock-in. Overkill at 1,200 QPS.

Veredito: um nó PostgreSQL (ou MySQL) + cache Redis de ~1,5GB na frente → 95–99% de hit, banco quase ocioso, tudo abaixo de 50ms. Migre para NoSQL quando o pico de leitura superar uma frota SQL replicada + cache — aproximadamente os problemas de 10M–100M DAU. O cache compra 2–3 ordens de magnitude de folga; gaste isso antes de gastar uma migração.Verdict: one PostgreSQL (or MySQL) node + a ~1.5GB Redis cache in front → 95–99% hit, near-idle DB, everything under 50ms. Move to NoSQL when peak reads outgrow a replicated SQL fleet + cache — roughly the 10M–100M DAU problems. The cache buys 2–3 orders of magnitude of headroom; spend that before spending a migration.

6O modelo mental em quatro linhasThe mental model in four lines

1. Hits são sempre rápidos (~2ms) — a pergunta protege os misses.
2. Miss é rápido só se o banco não está sobrecarregado → taxa é um dial de carga.
3. Taxa necessária = 1 − (carga_permitida / pico_QPS) — derive, não decore.
4. Taxa alcançável vem da skew do tráfego (power law) + tamanho do working set (RAM).1. Hits are always fast (~2ms) — the question protects the misses.
2. A miss is fast only if the DB isn't overloaded → the rate is a load dial.
3. Needed rate = 1 − (allowed_load / peak_QPS) — derive it, don't memorize.
4. Achievable rate comes from traffic skew (power law) + working-set size (RAM).
